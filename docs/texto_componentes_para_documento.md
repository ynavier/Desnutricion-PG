## Título (estilo Ttulo3):
Arquitectura de Componentes del Sistema NIVI

## Párrafos (estilo Normal):

El sistema NIVI se encuentra estructurado mediante una arquitectura de tres capas desacopladas que se comunican a través de una interfaz de programación de aplicaciones (API) de tipo REST con autenticación basada en tokens JSON Web Token (JWT). Esta organización permite que cada capa evolucione de forma independiente, favorece la escalabilidad horizontal del sistema y facilita el mantenimiento a largo plazo de la plataforma.

La capa de presentación corresponde a una aplicación web de página única (Single Page Application, SPA) desarrollada con React 18 y empaquetada mediante Vite, desplegada en la plataforma Vercel. Esta capa organiza la experiencia de usuario en tres paneles diferenciados según el rol asignado al actor del sistema. El panel clínico (CLI), destinado al personal de salud, centraliza el registro de pacientes, la captura de controles antropométricos, la consulta de alertas tempranas generadas automáticamente por el motor predictivo y el uso del asistente clínico de voz NIVI, el cual integra transcripción mediante el modelo Whisper de Groq y respuestas en lenguaje natural a través del modelo Llama 3.3. El panel analítico (ANL), orientado a epidemiólogos e investigadores, concentra exclusivamente las funciones de visualización epidemiológica y generación de reportes: incluye un dashboard con indicadores de tendencia, distribución territorial y análisis de factores de riesgo; integración con Power BI para visualizaciones externas; y la exportación de reportes nutricionales, epidemiológicos y de seguimiento de pacientes en formato Excel con análisis automático mediante inteligencia artificial. El panel administrador (ADM) concentra la gestión operativa del sistema: administración de cuentas de usuario, carga y habilitación de archivos SIVIGILA para el pipeline de entrenamiento, configuración y lanzamiento de jobs de reentrenamiento de modelos de Machine Learning, activación de modelos en producción y generación del reporte exclusivo de métricas y comparativas de modelos. La consistencia del estado de autenticación entre paneles es gestionada por un contexto global (AuthContext) que persiste la sesión en el almacenamiento local del navegador, mientras que todas las solicitudes HTTP son canalizadas por un cliente Axios centralizado que adjunta automáticamente el token de autorización e implementa cierre de sesión automático ante respuestas 401.

La capa de negocio está implementada mediante el framework FastAPI sobre Python 3.11, contenedorizada con Docker y desplegada en Google Cloud Run, lo que permite escalar automáticamente en función del tráfico sin requerir infraestructura dedicada. Esta capa expone trece grupos de endpoints organizados por dominio funcional. Durante el inicio del servidor, el mecanismo de ciclo de vida (lifespan) carga en memoria los modelos de Machine Learning serializados, garantizando baja latencia en cada solicitud de predicción. El módulo de predicción interno aplica las tablas de referencia de la Organización Mundial de la Salud para el cálculo de puntajes Z, codificación de variables categóricas mediante LabelEncoder, imputación de valores faltantes y escalado robusto (RobustScaler) antes de clasificar el estado nutricional del menor en seis categorías clínicas. Para las funciones de inteligencia artificial generativa, el sistema se conecta con la API de Google Gemini para la producción de recomendaciones clínicas personalizadas por paciente y el análisis narrativo de reportes epidemiológicos, implementando un mecanismo de caché en memoria de veinticuatro horas y respuestas de contingencia estáticas diferenciadas por nivel de severidad ante indisponibilidad del servicio externo. Adicionalmente, el sistema emplea el modelo Llama 3.3 70B de Groq para la generación de análisis de estadísticas epidemiológicas en el panel analítico y para la respuesta conversacional del asistente clínico NIVI en el panel clínico.

La capa de datos reside en Supabase, un servicio administrado de PostgreSQL, estructurado en seis tablas principales: perfiles de usuario con rol asignado, pacientes con veinticinco campos que incluyen datos personales, neonatales y sociodemográficos, controles clínicos con más de treinta campos antropométricos y el resultado de la predicción ML asociada, alertas generadas automáticamente por el motor de predicción, modelos de Machine Learning registrados con sus métricas de desempeño, y datasets de entrenamiento con su estado de procesamiento y habilitación. El esquema de base de datos fue versionado mediante cuatro migraciones SQL almacenadas en el repositorio. Los datos históricos que alimentan el sistema provienen de archivos Excel del Evento 113 del SIVIGILA, procesados mediante un pipeline ETL que unifica, limpia e imputa los registros de desnutrición aguda correspondientes al periodo 2020–2025. Los modelos predictivos fueron desarrollados y validados a través de un pipeline analítico documentado en siete notebooks de Jupyter y exportados como artefactos en formato joblib, los cuales son consumidos por la capa de negocio en el entorno de producción.
